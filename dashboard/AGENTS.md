# 보이스피싱 분석 대시보드 작업 지침

이 파일의 지침은 `dashboard/` 디렉터리와 그 하위 파일을 작업할 때 적용합니다.

일반적인 코딩 방식, Git 보호, 가상환경, 디버깅, 보안, 설명 방식 등은 Codex Custom instructions를 따릅니다.

이 문서에는 **본 프로젝트의 Streamlit 분석 대시보드에서만 필요한 규칙**을 정의합니다.

---

# 1. 대시보드 목적

이 대시보드는 최종 서비스를 직접 실행하는 화면이 아닙니다.

> **경찰청·우체국·보이스피싱 통화 데이터 등을 기반으로 보이스피싱 피해 현황과 위험 신호를 분석하고, 그 결과가 AI 기반 송금 방지 서비스와 어떻게 연결되는지 설명하는 데이터 분석 대시보드**

입니다.

따라서 대시보드 구현 시 다음을 우선합니다.

* 분석 결과를 빠르게 이해할 수 있는 구성
* 그래프 중심의 시각적 전달
* 분석 결과와 서비스 필요성의 자연스러운 연결
* 과도하게 복잡한 UI보다 발표·시연에 적합한 명확한 화면
* 데이터가 실제로 말하는 범위 안에서만 해석

단순히 화면을 화려하게 만드는 것보다 **분석 결과를 정확하고 이해하기 쉽게 전달하는 것**을 우선합니다.

---

# 2. 데이터별 역할

각 데이터의 역할을 혼동하지 않습니다.

## 경찰청 데이터

역할:

> **대한민국 전체 보이스피싱 피해 규모와 장기적인 변화 파악**

주요 활용:

* 연도별 발생건수
* 연도별 피해금액
* 사기유형별 변화
* 피해자 연령 구성
* 지역별 발생·피해 현황

경찰청 데이터는 주로 집계 통계이므로 개인 단위 예측이나 ML 학습 데이터처럼 사용하지 않습니다.

---

## 우체국 데이터

역할:

> **실제 보이스피싱 피해사례에서 나타나는 피해자 및 피해 특성 파악**

주요 활용:

* 피해금액 분포
* 연령대
* 성별
* 사기유형
* 사칭기관
* 피해금액과 각 특성 간 관계

우체국 데이터는 피해사례 분석과 통계적 관계 확인에 사용하며, 별도의 ML 모델을 억지로 만들기 위한 데이터로 사용하지 않습니다.

---

## 보이스피싱 통화 데이터

역할:

> **사기 통화 내부에서 나타나는 위험 신호와 패턴 파악**

주요 활용:

* 사기유형
* 사칭 대상
* 심리전략
* 요구행동
* 금액 언급
* 이벤트 커버리지
* 이벤트 조합
* 향후 ML 위험 탐지 Feature 후보

경찰청·우체국 데이터와 통화 데이터의 역할을 억지로 하나의 데이터셋처럼 합치지 않습니다.

---

사용자가 명시적으로 요청하지 않는 한 메뉴를 임의로 추가·삭제·분할하거나 이름을 변경하지 않습니다.

# 5. 기존 Streamlit 구조 유지

현재 대시보드의 기본 구조를 가능한 한 유지합니다.

현재 주요 구조:

```text
dashboard/
├─ app.py
├─ components/
│  ├─ overview.py
│  ├─ pages.py
│  └─ sidebar.py
├─ styles/
│  └─ style.py
└─ requirements.txt
```

현재 페이지 전환 방식:

```text
st.radio()
→
선택된 page key
→
PAGE_RENDERERS
→
해당 renderer 실행
```

사용자가 명시적으로 변경을 요청하지 않는 한 이 방식을 불필요하게 다른 네비게이션 구조로 교체하지 않습니다.

`initial_sidebar_state="locked"` 설정도 유지합니다.

# 6. 레이아웃 정책

## 개요 페이지

개요는 소개 페이지이므로 현재의 제한된 폭을 유지합니다.

현재 기준:

```text
overview_container
최대폭 약 1120px
```

개요의 카드형 구조와 적절한 좌우 여백을 유지합니다.

---

## 분석 페이지

분석 페이지는 그래프와 표를 넓게 보여줄 수 있도록 사용 가능한 본문 폭을 적극 활용합니다.

기본 구조:

```text
Sidebar │ 약 32px │──────── 분석 콘텐츠 ────────│ 약 32px
```

원칙:

* 분석 페이지는 `analysis_container` 사용
* 불필요한 `max-width` 제한을 두지 않음
* 데스크톱 기준 바깥 좌우 최소 여백 약 32px 유지
* 모바일에서는 적절한 반응형 여백 유지
* 화면 끝까지 완전히 붙이는 0px 레이아웃은 사용하지 않음
* 그래프와 표는 가능한 한 넓게 표시

# 7. 카드 UI 사용 원칙

페이지 전체를 하나의 거대한 카드로 감싸지 않습니다.

다음처럼 **강조가 필요한 개별 요소에만 카드 UI를 사용**합니다.

예:

* KPI
* 핵심 인사이트
* 중요한 주의사항
* 요약 결과

그래프 전체를 다시 큰 카드 안에 넣어 불필요하게 폭을 줄이지 않습니다.

개요 페이지의 카드 디자인은 이 규칙의 예외이며 현재 디자인을 유지합니다.

---

# 8. 그래프 구현 원칙

그래프는 캡처 이미지나 미리 저장한 PNG/JPG를 기본 방식으로 사용하지 않습니다.

가능하면 다음 흐름으로 코드에서 직접 생성합니다.

```text
원본 데이터
→
필요한 전처리 / 기존 분석 계산 재현
→
DataFrame
→
Plotly 등 시각화 코드
→
Streamlit 출력
```

그래프는 향후 데이터가 변경되어도 다시 계산될 수 있는 형태를 우선합니다.

인터랙티브한 분석 대시보드에서는 기본적으로 Plotly 사용을 우선 검토합니다.

새로운 시각화 라이브러리를 추가해야 한다면 기존 의존성을 먼저 확인합니다.

---

# 9. 분석 Notebook과 대시보드의 역할 구분

Notebook은 **분석·검정·결과 확정 공간**입니다.

대시보드는 **확정된 결과를 재현하고 설명하는 공간**입니다.

따라서 대시보드 구현 과정에서 새로운 가설검정이나 통계 분석을 임의로 추가하지 않습니다.

기본 원칙:

```text
Notebook에서 분석 방법과 결과 확정
→
대시보드에서 동일 계산 재현
→
그래프와 핵심 해석 제공
```

대시보드의 수치를 편의를 위해 별도로 임의 수정하거나 분석 결과와 다른 계산식을 사용하지 않습니다.

# 10. 원본 분석 파일 보호

`dashboard/` 작업을 위해 다음 파일을 임의 수정하지 않습니다.

예:

* `c_이종열/` 내부 CSV
* 경찰청 분석 Notebook
* 우체국 분석 Notebook
* 가설 Markdown
* 통계 분석 결과 파일
* 다른 팀원의 분석 파일

필요한 경우 해당 파일을 **읽어서 참조**할 수는 있습니다.

대시보드에서 사용하기 위해 원본 데이터나 기존 분석 결과 자체를 변경하지 않습니다.

원본 분석 수정이 필요한 문제가 발견되면 대시보드에서 조용히 우회하지 말고 사용자에게 알려야 합니다.

# 11. 데이터 경로 처리

`dashboard/`와 분석 데이터 폴더가 서로 다른 위치에 있을 수 있으므로 실행 위치에 지나치게 의존하는 상대경로를 사용하지 않습니다.

가능하면 `pathlib.Path`와 현재 파일의 위치를 기준으로 안정적인 경로를 구성합니다.

예:

```python
from pathlib import Path
```

단, 실제 프로젝트 디렉터리 구조를 먼저 확인하고 경로를 결정합니다.

Windows 사용자 PC의 절대경로를 코드에 직접 하드코딩하지 않습니다.

예를 들어 다음과 같은 경로를 코드에 직접 작성하지 않습니다.

```text
C:\Users\...
```

# 12. 분석 결과 표현 원칙

그래프만 보여주고 끝내지 않습니다.

핵심 분석 결과에는 필요한 경우 다음 흐름을 사용합니다.

```text
분석 주제
→
왜 확인했는가?
→
그래프 / KPI
→
핵심 인사이트
→
필요한 경우 서비스 연결
```

다만 모든 그래프에 같은 설명 박스를 기계적으로 반복하지 않습니다.

내용이 단순하면 설명을 줄이고, 해석상 주의가 필요한 결과에는 충분한 설명을 제공합니다.

---

# 13. 통계 결과 표현

p-value만으로 결과의 중요성을 판단하지 않습니다.

가능한 경우 다음을 함께 고려합니다.

* 표본 수
* 중앙값 / 평균
* 분포
* 효과크기
* 다중검정 보정
* 통계 검정의 가정
* 소표본 여부

통계적 유의성을 인과관계로 표현하지 않습니다.

예:

```text
잘못된 표현:
연령 때문에 피해금액이 증가한다.

권장 표현:
연령대에 따라 피해금액 분포에 통계적으로 유의한 차이가 확인되었다.
```

# 14. 경찰청 데이터 해석 주의

경찰청 연령 데이터는 **피해자 구성비**입니다.

이를 다음과 같이 표현하지 않습니다.

```text
50대가 보이스피싱에 걸릴 확률이 가장 높다.
```

인구 대비 발생률을 계산하지 않았다면 다음처럼 표현합니다.

```text
전체 피해자 중 50대가 가장 큰 비중을 차지했다.
```

지역 데이터 역시 인구·경제규모·거래량 등을 보정하지 않았다면 지역 자체의 위험률처럼 표현하지 않습니다.

---

# 15. 우체국 데이터 해석 주의

우체국 데이터는 일부 범주의 표본 수가 매우 작을 수 있습니다.

표본 수가 작은 범주의 평균이나 중앙값이 높다는 이유만으로 다음과 같이 단정하지 않습니다.

```text
이 사칭기관이 가장 위험하다.
이 사기유형이 가장 위험하다.
```

필요한 경우 그래프에 `n` 또는 표본 수를 함께 표시하고 소표본 주의사항을 제공합니다.

피해금액은 오른쪽으로 치우친 분포이므로 평균만 단독으로 강조하지 않습니다.

필요한 경우 중앙값과 분포를 함께 보여줍니다.

---

# 16. 통화 데이터 해석 주의

현재 확보된 보이스피싱 통화 데이터는 전체 실제 통화가 아니라 **주요 발화가 발췌·편집된 형태일 수 있습니다.**

따라서 발췌 데이터의 순서를 실제 전체 통화의 정확한 시간 흐름으로 간주하지 않습니다.

다음과 같은 내용을 확정적으로 표현하지 않습니다.

* 전체 통화시간
* 실제 통화 시작·종료 시점
* 전략이 등장한 절대적인 시간
* 실제 전체 통화의 초반·중반·후반
* 피해자가 순응하기 시작한 정확한 시점
* 외부 개입의 최적 시점

시간 순서 분석을 사용해야 한다면 반드시 다음과 같이 범위를 제한합니다.

> 현재 확보된 발췌 구간 안에서 관찰된 순서

---

# 17. 이벤트 커버리지 해석

통화 데이터에서 이벤트가 탐지되지 않았다는 사실을 실제 사건에서 해당 내용이 존재하지 않았다는 의미로 해석하지 않습니다.

예:

```text
금액 이벤트 탐지율 27%
```

을 다음처럼 표현하지 않습니다.

```text
보이스피싱의 73%에서는 금액을 언급하지 않는다.
```

다음처럼 표현합니다.

```text
현재 확보·추출된 데이터에서 명시적인 금액 이벤트가 약 27%의 사건에서 탐지되었다.
```

즉,

> 탐지되지 않음 ≠ 실제 존재하지 않음

원칙을 유지합니다.

---

# 18. 서로 다른 금액 변수 구분

우체국 데이터의 `피해금액`과 통화 분석의 `금액 이벤트` 또는 통화 중 언급된 금액을 같은 변수처럼 사용하지 않습니다.

예:

```text
우체국 피해금액
= 실제 피해 규모

통화 금액 이벤트
= 통화 내용에서 추출된 금액 관련 언급
```

따라서 별도 분석 근거 없이

```text
통화에서 큰 금액이 언급될수록 실제 피해금액이 커진다.
```

와 같은 연결을 만들지 않습니다.

# 19. 서비스 연결 원칙

분석 결과를 서비스와 연결할 수는 있지만 분석 결과가 직접 증명하지 않은 기능까지 과장하지 않습니다.

예를 들어 통화 데이터에서

* 사칭
* 심리전략
* 요구행동
* 금액

이 함께 관찰된다면 다음과 같은 연결은 가능합니다.

> 하나의 키워드만 탐지하기보다 여러 위험 신호를 함께 판단하는 구조가 필요하다.

반면 별도 검증 없이 다음과 같이 표현하지 않습니다.

> 이 신호를 사용하면 보이스피싱을 정확히 차단할 수 있다.

서비스 연결은 **분석 결과가 지원하는 범위 안에서** 작성합니다.

---

# 20. ML 구현 원칙

ML은 프로젝트에 필요할 때 사용하며 기존 경찰청·우체국 분석에 억지로 적용하지 않습니다.

ML 작업에서는 다음을 명확하게 구분합니다.

```text
Target
Feature
Training
Validation / Test
Prediction
Evaluation
```

보이스피싱 탐지에서는 단순 Accuracy보다 실제 서비스 목적에 적합한 Recall, Precision, False Positive 등의 의미를 함께 검토합니다.

모델 성능이 높다는 이유만으로 실제 금융 서비스에서 즉시 강제 차단할 수 있다고 단정하지 않습니다.

---

# 21. 구현 단위

대시보드는 한 번에 전체를 완성하려 하지 않습니다.

가능하면 다음 흐름으로 작은 단위로 작업합니다.

```text
콘텐츠 블록 하나 구현
→
실행 / 검증
→
화면 확인
→
다음 콘텐츠 블록 구현
```

한 요청에서 관련 없는 여러 페이지를 동시에 대규모 수정하지 않습니다.

---

# 22. 작업 범위 판단

사용자가 특정 콘텐츠 구현을 요청한 경우 해당 콘텐츠에 필요한 범위만 수정합니다.

예:

```text
경찰청 P1·P2 구현 요청
```

이라면 특별한 이유 없이 다음까지 같이 작업하지 않습니다.

* 우체국 그래프
* 통화 분석
* ML
* 서비스 데모
* 사이드바 재설계
* 개요 UI 변경

향후 작업을 위한 구조 변경이 필요하다면 최소 범위에서 수행합니다.

---

# 23. 최우선 원칙

대시보드 작업에서 판단이 애매할 경우 다음 우선순위를 사용합니다.

```text
1. 원본 분석 결과의 정확성
2. 데이터 한계의 올바른 표현
3. 기존 대시보드 구조 보존
4. 사용자가 이해하기 쉬운 시각화
5. 서비스와의 자연스러운 연결
6. 디자인과 시각적 완성도
```

**보기 좋은 그래프를 만들기 위해 분석 의미를 왜곡하지 않습니다.**
