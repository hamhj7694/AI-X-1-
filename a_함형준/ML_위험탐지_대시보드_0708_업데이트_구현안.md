## 2. 가장 중요한 변경점

기존에는 07 단계가 Calibration, Risk Score, Threshold를 한 번에 담당하는 것처럼 구성되어 있었다. 최신 Drive에서는 역할이 다음처럼 분리됐다.

```text
06 모델 비교 및 최종 모델 선택
    ↓
07 Calibration + 연속형 Risk Score 생성
    ↓
08 Validation 기반 Threshold + 실시간 Window 경고정책 결정
    ↓
단일 배포 Pipeline 생성
```

### 07의 최신 역할

- Window 확률 보정 방식 선택: `PLATT`
- Case 확률 보정 방식 선택: `IDENTITY`
- Risk Score 생성
- Threshold는 결정하지 않음
- 설정 파일: `calibration_manifest_07.json`
- `threshold_selected = false`
- `threshold_stage = 08`

### 08의 최신 역할

- Window를 실제 통화 순서대로 묶어 실시간 경고정책을 평가
- Validation에서 Threshold 및 연속성 정책을 선택
- Case Threshold는 전체 통화 기반의 보조 판정 기준으로 선택
- 설정 파일: `threshold_policy_config_08.json`
- 최종 단일 배포 파일: `final_voice_phishing_risk_pipeline.pkl`

### 기존 대시보드에서 반드시 교체해야 하는 값

## 3. 전체 변수 생성·축소 흐름

대시보드에는 “최종 12개 Feature를 사용했다”는 결과만 보여주지 말고, 어떤 안전장치를 거쳐 줄였는지를 보여준다.

```text
EDA에서 위험 패턴 발견
    ↓
피싱 내부 Window 후보 컬럼 생성: 51개
    ↓
Case 집계 후보 컬럼 생성: 117개
    ↓
정상·피싱에 동일하게 적용 가능한 공통 후보: 29개
    ↓
통계검정 + 효과크기 + 중복·희소성 점검
    ↓
Group CV 안정성 검증: 12개 선별
    ↓
Semantic QC 및 출처·길이 Proxy 제거
    ↓
최종 Case 12개 / Window 12개 확정
```

### 숫자를 해석할 때의 주의점

- 51개는 피싱 Window 후보 테이블의 전체 컬럼 수다.
- 117개는 Window 후보를 통화 단위로 max/mean/sum 집계하면서 늘어난 Case 후보 컬럼 수다.
- 이 둘은 그대로 정상·피싱 분류 모델에 투입한 Feature 수가 아니다.
- 정상과 피싱에 동일 정의로 적용할 수 있는 공통 비교 후보를 다시 구성했고, 이 단계의 Scorecard가 29개였다.
- 최종 모델 입력은 29개 중 CV 안정성, 의미 중복, Semantic QC, 누수 가능성을 확인해 12개로 축소했다.

대시보드의 핵심 축소 메시지는 다음처럼 표현한다.

> 피싱 내부에서 51개 Window 후보와 117개 Case 집계 후보를 생성했으며, 정상·피싱에 같은 방식으로 추출할 수 있는 29개 공통 후보로 재정의했다. 이후 통계적 차이, CV 안정성, 의미 중복, Semantic QC, 출처·길이 누수 가능성을 검토해 최종 12개 Feature로 축소했다.

## 4. Feature를 이렇게 선별한 이유

Feature 선택은 단순히 상관계수가 높거나 p-value가 작은 변수만 남기는 방식이 아니었다.

### 선별 기준

1. EDA에서 보이스피싱 행동 구조와 연결되는가?
2. 현재 Window 시점까지의 정보만 사용해 실시간 계산할 수 있는가?
3. 정상과 피싱 모두에 동일한 추출기를 적용할 수 있는가?
4. 결측·상수·과도한 희소성 문제가 없는가?
5. 다른 Feature와 완전히 같거나 의미가 지나치게 겹치지 않는가?
6. 정상과 피싱의 차이가 효과크기와 다중검정 보정 후에도 남는가?
7. `source_id` 기준 Group CV에서 Fold가 바뀌어도 안정적인가?
8. 정상 상담의 안내·경고 문맥을 피싱 위험 표현으로 잘못 잡지 않는가?
9. 통화 길이, 파일명, 출처처럼 데이터 제작방식을 암시하는 Proxy가 아닌가?

### 제외 또는 QC 전용으로 둔 변수

- 전체 Turn 수
- 텍스트 길이
- 파일명과 데이터 출처
- 통화 진행률처럼 전체 길이를 알아야 계산되는 값
- Window 개수
- Window Stack 사용 가능 여부
- 완전 중복 변수
- 의미가 겹치거나 CV에서 불안정한 변수

이 과정의 기획 의도는 모델이 “금융감독원 자료 형식”과 “AIHub 자료 형식”을 구분하는 것이 아니라, 통화 안에서 관찰되는 실제 위험신호 조합을 학습하도록 만드는 것이었다.

## 8. 머신러닝 점수화 방식

### 사용하지 않은 방식

다음과 같은 사람이 정한 가산점 방식은 사용하지 않았다.

```text
사칭 +20점
공포 +15점
민감정보 요구 +25점
```

### 사용한 방식

```text
최종 Feature 입력
    ↓
Random Forest가 P(PHISHING)을 예측
    ↓
Calibration
    ↓
Calibrated Probability
    ↓
Risk Score = Calibrated Probability × 100
```

### 기본 수식

```text
Raw probability
p_raw = RF.predict_proba(X)[:, 1]
```

Window 모델은 Platt Scaling을 사용한다.

```text
p_window_calibrated = sigmoid(a × logit(p_window_raw) + b)
Window Risk Score = 100 × p_window_calibrated
```

Case 모델은 Identity가 선택됐다.

```text
p_case_calibrated = p_case_raw
Case Risk Score = 100 × p_case_calibrated
```

### 왜 이런 점수화 방식을 선택했는가?

1. 위험신호의 효과가 단순 선형·단조 가산 구조가 아니었음
2. 같은 신호도 다른 신호와 결합될 때 위험도가 달라질 수 있었음
3. Feature마다 사람이 임의의 점수를 주면 설명은 쉬워도 실제 검증 성능과 연결되지 않음
4. 모델이 학습한 확률을 사용하면 Feature의 가중치와 비선형 조합이 데이터에서 결정됨
5. Calibration을 적용하면 모델 간 Raw Probability의 과신·과소신뢰를 줄이고 Threshold와 연결하기 쉬움
6. 0~100 점수는 서비스 화면에서 사용자가 이해하기 쉬움

따라서 Risk Score는 “12개 Feature를 사람이 더한 점수”가 아니라 “12개 Feature의 조합을 모델이 학습해 산출한 보정 확률”이다.

### 해석상 한계

현재 Risk Score는 내부 데이터 분포에서 보정된 상대적 위험도다. 현실 세계의 절대적인 보이스피싱 발생확률로 단정하면 안 된다. 외부 데이터가 바뀌면 재Calibration이 필요하다.

## 9. 최신 08 Threshold와 실시간 경고정책

### 정책 선정 목표

Validation에서 다음 목표를 동시에 만족하는 정책을 찾았다.

```text
목표 Call Recall ≥ 0.90
정상 통화 FPR ≤ 0.20
```

동시에 만족하는 정책이 없어, 목표에서 가장 덜 벗어난 값을 F2·FPR·조기성 순으로 비교해 `COMPROMISE`로 선택했다.

### Window 실시간 경고

```text
정책: SINGLE
Window: 10 Turn
Stride: 5 Turn
최초 경고 가능 시점: 10 Turn
경고 기준: Window Risk Score ≥ 69
```

Validation:

- Call Recall: 0.6437
- Call Precision: 0.9032
- 정상 통화 FPR: 0.1071

내부 Test:

- Call Recall: 0.5325
- Call Precision: 0.8723
- 정상 통화 FPR: 0.1053
- 탐지된 피싱의 첫 경고 중앙 Turn: 10
- 첫 경고 상대 위치 중앙값: 0.25

### Case 보조 판정

```text
Case Risk Score ≥ 58
역할: 통화 종료 후 또는 전체 문맥 기반 보조 판정
```

내부 Test:

- Recall: 0.7565
- Precision: 0.9560
- FPR: 0.0690
- F1: 0.8447

### 반드시 함께 표시할 경고

- 69와 58은 절대적인 운영 확정값이 아님
- 두 기준 모두 Validation 목표 Recall 0.90과 FPR 0.20을 동시에 만족하지 못한 `COMPROMISE`
- 외부 데이터 확보 후 재Calibration과 Threshold 재설정 필요
- Window는 실시간 1차 경고, Case는 전체 통화 기반 2차 보조 판정임

## 10. `ml_validation.py`에 추가할 화면 구성

현재 화면의 기존 섹션은 유지하고, 아래 내용을 하단에 추가한다.

### A. Feature 축소 Funnel

가로 또는 4단계 카드로 표시한다.

```text
피싱 내부 후보 생성
Window 51 / Case 117
    →
정상·피싱 공통 후보 29
    →
통계·CV·Semantic QC
    →
최종 Case 12 / Window 12
```

설명에는 51·117이 같은 층위의 독립 Feature 수가 아니라 후보 테이블 및 집계 컬럼 수라는 점을 Tooltip이나 Caption에 명시한다.

### B. 최종 12개 Feature 지도

긴 테이블 대신 5개 묶음 카드로 구성한다.

1. 사칭: `imp_public`, `imp_financial`
2. 심리전략: `strategy_authority`, `strategy_fear`, `strategy_info_extraction_sem`
3. 위험 행동: `sensitive_info_request_sem`, `auth_info_request_sem`
4. 복합성: `strategy_diversity_sem`, `action_diversity_sem`, `signal_family_count_sem`
5. 상호작용: `ix_identityclaim_authority_sem`, `ix_info_sensitive_sem`

Window는 `signal_family_count_sem` 대신 `signal_family_count_delta_sem`을 사용한다는 별도 Badge를 넣는다.

### C. Feature 선정 안전장치

다음 5개를 짧은 체크 카드로 보여준다.

- 정상·피싱 동일 추출기
- 효과크기 및 다중검정
- source_id Group CV
- Semantic QC
- 출처·길이 Proxy 제거

### D. 머신러닝 점수화 수식

기존 Risk Score Flow 아래에 다음 수식을 추가한다.

```text
p_raw = RandomForest.predict_proba(X)[:, 1]

Window:
p_cal = sigmoid(a × logit(p_raw) + b)

Case:
p_cal = p_raw

Risk Score = 100 × p_cal
```

수식 아래 핵심 문구:

> Risk Score는 Feature별 수동 가산점이 아니라, 모델이 12개 위험신호의 가중치와 조합을 학습해 산출한 보정 확률이다.

### E. 07과 08 역할 분리

```text
07 Calibration
Window=Platt / Case=Identity
    ↓
연속형 Risk Score 0~100
    ↓
08 Validation 정책 탐색
    ↓
Window 69점 실시간 경고 / Case 58점 보조 판정
```

### F. Threshold Trade-off 카드

Window와 Case를 좌우 2열로 표시한다.

Window:

- 정책 `SINGLE`
- Risk Score 69
- Test Recall 0.5325
- Test Precision 0.8723
- 정상 FPR 0.1053

Case:

- Risk Score 58
- Test Recall 0.7565

## 15. 대시보드 하단 `[구현 과정]` 최종 콘텐츠 명세

기존 모델 성능·Calibration 화면 아래에 다음 순서로 추가한다.

### 15-1. Feature 축소 Funnel

카드 문구를 아래처럼 확정한다.

1. `후보 생성` — Window 51열 / Case 집계 117열
2. `공통화` — 정상·피싱 동일 추출 후보 29개
3. `검증` — 통계·효과크기·Group CV·Semantic QC
4. `최종 확정` — Case 12개 / Window 12개

Caption:

> 51열과 117열은 서로 같은 층위의 독립변수 개수가 아니라, 피싱 내부 Window 후보 테이블과 이를 통화 단위로 집계한 후보 테이블의 컬럼 수다. 실제 정상·피싱 공통 선별은 29개 후보에서 시작했다.

### 15-2. 최종 Feature 지도

화면에서는 12행 전체 표보다 의미 묶음 카드를 우선한다.

- 사칭 2개: 공공기관, 금융기관
- 심리전략 3개: 권위, 공포, 정보추출
- 위험행동 2개: 민감정보, 인증정보 요구
- 복합성 3개: 전략 다양성, 행동 다양성, 위험신호 계열 수
- 상호작용 2개: 신분주장×권위, 정보추출×민감정보

각 카드 안에는 영문 Feature명을 작은 글씨로 함께 표시한다.

### 15-3. Case와 Window의 차이

```text
공통 11개 Feature
+ Case: signal_family_count_sem
+ Window: signal_family_count_delta_sem
```

설명:

> Case는 통화 전체의 누적 위험신호 계열 수를 사용했고, Window는 직전 구간 대비 새롭게 늘어난 위험신호 계열 수를 사용해 실시간 변화에 반응하도록 했다.

### 15-4. Feature 선정 안전장치

화면 문구를 다음 5개로 확정한다.

- 동일 추출기: 정상·피싱에 동일 Rule/LLM Semantic 계약 적용
- 통계 검증: 효과크기와 BH-FDR을 함께 확인
- Group CV: 같은 통화가 Train/Test에 섞이지 않게 source_id 기준 분리
- Semantic QC: 정상 금융안내·경고와 실제 위험요구 문맥 구분
- Proxy 제거: 길이·파일명·출처·Window 개수 등 제작방식 단서 제외

### 15-5. 점수화 수식과 기획 의도

화면 수식:

```text
p_raw = RandomForest.predict_proba(X)[:, 1]

Window: p_cal = sigmoid(a × logit(p_raw) + b)  # Platt
Case:   p_cal = p_raw                           # Identity

Risk Score = 100 × p_cal
```

기획 의도 문구:

> 위험신호는 단순히 많을수록 항상 위험한 구조가 아니었고, 같은 신호도 다른 신호와 결합될 때 의미가 달라졌다. 그래서 사람이 `사칭 +20점`처럼 임의 배점하지 않고, Random Forest가 12개 신호의 가중치와 비선형 조합을 학습하도록 했다. 이후 확률 보정을 거쳐 서비스에서 읽기 쉬운 0~100 Risk Score로 변환했다.

### 15-6. 07→08 운영 연결

```text
07: Window Platt / Case Identity
→ 연속형 Risk Score 0~100
→ 08: Validation Recall·FPR Trade-off 탐색
→ Window 69점 SINGLE 실시간 경고
→ Case 58점 전체 통화 보조판정
```

상태 Badge는 두 모델 모두 `COMPROMISE · 내부 Prototype`으로 표시한다.

### 15-7. 최종 해석 문구

> 현재 69점과 58점은 내부 Validation에서 목표 Recall 0.90과 정상 통화 FPR 0.20을 동시에 만족하는 정책이 없어 선택한 절충값이다. 외부 데이터 검증 전 확정 운영기준이나 절대적인 보이스피싱 확률로 해석하지 않는다.
