# 보이스피싱 분석 데이터셋 상세 설계

## Summary

보이스피싱 사례는 하나의 사건 안에서 검찰·경찰·금융감독원·은행·카드사·가족·지인 등을 여러 번 또는 순차적으로 사칭할 수 있다. 따라서 `검찰_사칭`, `경찰_사칭`, `은행_사칭` 컬럼을 사건 테이블에 계속 추가하는 방식보다 다음과 같은 **관계형 구조**가 적합하다.

```text
원본 파일 vp_files
 └─ 사건 vp_cases
     ├─ 발화 vp_utterances
     ├─ 사칭 정보 vp_impersonations
     ├─ 요구 행동 vp_requested_actions
     └─ 설득·위험 신호 vp_strategy_events
     └─ 금액 상태       vp_amount_events
```

핵심 설계 원칙은 다음과 같다.

1. 한 사건에 여러 사칭 대상과 요구 행동을 저장할 수 있게 한다.
2. `경찰/검찰/은행/가족` 같은 대분류와 실제 기관명·부서·직책·관계·이름을 각각 다른 컬럼으로 저장한다.
3. 자동 추출 결과마다 근거 발화, 추출 방법, 신뢰도, 검수 상태를 기록한다.
4. 대시보드용 대표값은 `vp_cases`에 넣고, 상세 정보는 하위 테이블에서 관리한다.
5. 실제로 언급되지 않은 기관명·사람 이름·직책은 추측하지 않는다.
6. 모든 자동 생성 라벨은 `SILVER`로 표시한다.

이 구조를 사용하면 다음을 구분할 수 있다.

- 검찰·경찰·법원 등 수사·사법기관 중 무엇을 사칭했는가?
- 어떤 실제 기관명과 부서명을 말했는가?
- 검사·수사관·경찰관·은행원·대출상담사 중 어떤 직책을 주장했는가?
- 가족·친구·직장동료 등 누구와의 관계를 사칭했는가?
- 한 사건에서 검찰에서 금감원 또는 은행으로 사칭 대상이 전환됐는가?
- 각 사칭 직후 어떤 송금·인출·앱 설치·개인정보 제공을 요구했는가?
- 어떤 발화가 해당 라벨의 근거인가?

## 1. 데이터 계층

### 1.1 원천 계층

원본을 수정하지 않고 보관한다.

```text
MP3/MP4
cases.json
turns.csv
기존 자동 전사·화자분리 결과
정상 금융상담 JSON
경찰·우체국 공개 데이터
```

### 1.2 표준 데이터 계층

분석의 기준이 되는 정규화 테이블이다.

```text
vp_files.csv
vp_cases.csv
vp_utterances.csv
vp_impersonations.csv
vp_requested_actions.csv
vp_strategy_events.csv
normal_finance_calls.csv
```

### 1.3 머신러닝·대시보드 계층

표준 테이블을 분석 목적에 맞게 다시 집계한다.

```text
fraud_detection_ml.csv
fraud_type_ml.csv
segment_detection_ml.csv
case_clustering_ml.csv
dashboard_case_summary.csv
dashboard_external_stats.csv
```

표준 테이블은 가능한 한 반복 없이 보존하고, 머신러닝용 데이터에서만 one-hot 변수와 집계변수를 생성한다.

## 2. 공통 식별자

모든 테이블은 다음 ID를 공통으로 사용한다.

| 컬럼 | 설명 | 예시 |
|---|---|---|
| `file_id` | 원본 MP3/MP4 ID | `vp_000001` |
| `case_id` | 파일 내부 사건 ID | `vp_000001_case_001` |
| `turn_id` | 사건 내부 발화 ID | `vp_000001_case_001_turn_0001` |
| `impersonation_id` | 사칭 정보 ID | `imp_000001` |
| `action_id` | 요구 행동 ID | `act_000001` |
| `strategy_event_id` | 설득 전략 이벤트 ID | `str_000001` |
| `conversation_id` | 정상·사기 통합 분석 ID | `fraud_vp_000001_case_001` |

같은 원본 파일의 여러 사건이 학습과 시험 데이터에 나뉘지 않도록 `file_id`를 그룹 분할 기준으로 사용한다.

## 3. `vp_files.csv`: 원본 파일 테이블

한 행은 MP3 또는 MP4 하나이다.

| 컬럼 | 자료형 | 설명 |
|---|---|---|
| `file_id` | string | 파일 고유 ID |
| `source_category` | category | 원본 폴더 분류 |
| `source_file` | string | 원본 파일명 |
| `source_post_id` | string | 금융감독원 게시물 ID |
| `publication_date` | date | 게시일 |
| `media_type` | category | `MP3`, `MP4` |
| `duration_sec` | float | 전체 재생시간 |
| `case_count` | int | 자동 분리 사건 수 |
| `turn_count` | int | 발화 수 |
| `empty_transcript` | boolean | 빈 전사 여부 |
| `multi_case_file` | boolean | 다중 사건 여부 |
| `media_composition` | category | 전체 통화·범인 단독·편집 영상·불명 |
| `quality_flag` | category | 품질 상태 |

`publication_date`는 게시일이며 실제 범행 발생일로 사용하지 않는다.

## 5. `vp_utterances.csv`: 발화 테이블

한 행은 발화 하나이다.

| 컬럼 | 설명 |
|---|---|
| `file_id` | 원본 파일 ID |

| `end_sec` | 종료 시각 |
| `duration_sec` | 발화 길이 |
| `speaker_id` | 자동 화자 ID |
| `auto_role` | 자동 역할 |
| `role_heuristic_score` | 역할 추정 점수 |
| `raw_text` | 원본 자동 전사 |

## 6. `vp_impersonations.csv`: 사칭 정보 상세 테이블

한 행은 **사칭 정체성 또는 사칭 대상 한 건**이다. 한 사건에 여러 행이 존재할 수 있다.

### 6.1 핵심 컬럼

| 컬럼 | 설명 | 예시 |
|---|---|---|
| `impersonation_id` | 사칭 정보 ID | `imp_000001` |
| `file_id` | 원본 파일 ID | `vp_000001` |
| `case_id` | 사건 ID | `vp_000001_case_001` |
| `evidence_turn_id` | 근거 발화 ID | `...turn_0004` |
| `impersonation_group` | 사칭 대분류 | `PUBLIC_AGENCY` |
| `impersonation_subtype` | 세부 유형 | `PROSECUTION` |
| `claimed_org_name_raw` | 원문 기관명 | `서울중앙지방검찰청` |
| `claimed_org_name_normalized` | 정규화 기관명 | `서울중앙지방검찰청` |
| `claimed_department_raw` | 원문 부서명 | `첨단범죄수사부` |
| `claimed_department_normalized` | 정규화 부서명 | `첨단범죄수사부` |
| `claimed_role_title_raw` | 원문 직책·직급 | `김OO 수사관` |
| `claimed_role_title_normalized` | 정규화 직책 | `INVESTIGATOR` |
| `claimed_person_name_raw` | 발화에 나온 이름 | `[PERSON]` |
| `claimed_person_name_masked` | 비식별 이름 | `[PERSON_01]` |
| `claimed_relationship` | 피해자와의 관계 | `CHILD` |
| `identity_claim_type` | 사칭 방식 | `CALLER_SELF_CLAIM` |
| `is_primary_impersonation` | 사건 대표 사칭 여부 | `True` |
| `first_mention_turn` | 최초 언급 발화 순서 | `4` |
| `first_mention_sec` | 최초 언급 시각 | `18.4` |

```text

SIBLING

COWORKER
BOSS
CUSTOMER

```

예:

| 원문 | 대분류 | 세부 유형 | 관계 | 사람 이름 |
|---|---|---|---|---|
| `아들이 납치됐다` | `FAMILY` | `KIDNAPPING_CLAIM` | `SON` | `NOT_MENTIONED` |
| `민수인데 휴대폰이 고장났어` | `FAMILY` 또는 `ACQUAINTANCE` | `MESSENGER_IMPERSONATION` | 문맥에 따라 결정 | `[PERSON_01]` |
| `직장 상사 부탁으로 송금해 달라` | `ACQUAINTANCE` | `BUSINESS_CONTACT` | `BOSS` | `NOT_MENTIONED` |

관계가 문맥에 명확히 나오지 않으면 이름만으로 가족·지인을 추정하지 않고 `RELATION_UNKNOWN`으로 둔다.

`은행원 누구인지`는 다음처럼 나눠 저장한다.

```text

```

예를 들어 `OO은행 여신심사부 김OO 과장입니다`는 다음과 같다.

```text

claimed_department_normalized = LOAN_REVIEW_DEPARTMENT
claimed_role_title_normalized = MANAGER
claimed_person_name_masked = [PERSON_01]
```

### 6.7 사칭 방식 `identity_claim_type`

```text
CALLER_SELF_CLAIM          전화한 사람이 자신을 기관·인물로 소개
ASSOCIATE_IMPERSONATION    가족·지인인 것처럼 행세
THIRD_PARTY_REFERENCE      다른 기관·담당자를 권위 근거로 언급
TRANSFERRED_AGENT_CLAIM    다른 담당자에게 연결한다고 주장
VICTIM_ASSOCIATE_CLAIM     피해자의 가족·지인이 위험하다고 주장
UNKNOWN
```

기관 이름이 등장했다고 모두 사칭으로 처리하지 않는다.

예:

```text
`저는 서울중앙지검 수사관입니다`
→ CALLER_SELF_CLAIM

`금감원에서 확인된 내용입니다`
→ THIRD_PARTY_REFERENCE

`은행에 직접 확인해 보세요`
→ 단순 기관 언급일 수 있으므로 사칭 아님
```

```text
CLAIMED_COMPLETED     대화에서 했다고 말함
UNKNOWN
```

`CLAIMED_COMPLETED`는 실제 금융거래가 확인된 것이 아니라 대화에서 완료했다고 주장한 상태이다.

## 7.4 `vp_amount_events.csv`: 금액 이벤트 테이블

한 행은 한 발화에서 발견되거나 바로 앞 요구 발화와 연결된 금액 상태 한 건이다.

```text
amount_event_id
file_id
case_id
evidence_turn_id
amount_source_turn_id
evidence_role
turn_order
mention_sec
amount_krw
amount_text
amount_status
related_action_type
evidence_text
inferred_from_context
verified_loss_amount_krw
extraction_method
extraction_confidence
verification_status
label_status
```

`amount_status`는 다음과 같이 구분한다.

```text
MENTIONED             단순 언급
REQUESTED             송금·인출·전달 등을 요구
AGREED                피해자가 준비·이체 의사를 표현
CLAIMED_COMPLETED     대화에서 이체·전달 완료를 주장
```

금액 없는 피해자 응답은 직전 2개 발화 안의 요구금액과 연결할 수 있으며, 이 경우
`inferred_from_context=True`, `verification_status=AUTO_REVIEW_RECOMMENDED`로 표시한다.
`verified_loss_amount_krw`는 녹취만으로 채우지 않으며 금융거래 또는 신고자료로 확인된 경우에만 기록한다.

## 9. 값이 없을 때의 표기

값이 없는 이유를 구분한다.

| 값 | 의미 |
|---|---|
| `NOT_MENTIONED` | 대화에 언급되지 않음 |
| `UNKNOWN` | 언급은 있으나 분류 불가능 |
| `NOT_APPLICABLE` | 해당 컬럼이 적용되지 않음 |
| `REVIEW` | 자동 판단이 불안정해 검토 필요 |
| `pd.NA` | 기술적 결측 또는 아직 처리되지 않음 |

예를 들어 `검찰청 수사관입니다`라고만 했다면 다음과 같다.

```text
claimed_org_name_normalized = PROSECUTION_UNKNOWN
claimed_role_title_normalized = INVESTIGATOR
claimed_person_name_masked = NOT_MENTIONED
```

사람 이름을 모델이 임의로 만들면 안 된다.

## 10. 자동 추출 방법

### 10.1 1단계: 규칙·사전 기반 추출

팀이 직접 구현하기 좋은 첫 단계이다.

```python
impersonation_keywords = {
    "PROSECUTION": ["검찰", "검사", "지검", "수사관"],
    "POLICE": ["경찰", "경찰서", "형사", "사이버수사과"],
    "FSS": ["금융감독원", "금감원", "금융 조사관"],
    "BANK": ["은행", "은행원", "대출 담당", "여신 심사"],
}
```

정규표현식과 키워드 주변 문맥을 이용해 기관명·직책·관계를 추출한다.

장점:

- 코드와 기준을 설명하기 쉽다.
- 결과를 직접 수정하기 쉽다.
- 대시보드용 파생변수 생성에 적합하다.

한계:

- ASR 오타와 새로운 표현에 약하다.
- 기관의 단순 언급과 실제 사칭을 구분하기 어렵다.

### 10.2 2단계: NER 또는 텍스트 분류 모델

규칙 결과를 보완하기 위해 다음 모델을 사용할 수 있다.

- 기관명·사람명·직책 추출: 한국어 개체명 인식
- 사칭 대분류: 문장 다중분류
- 요구 행동: 다중 라벨 분류

그러나 현재 사람 정답이 충분하지 않으므로 모델 결과는 `SILVER`로 저장한다.

### 10.3 3단계: 문맥 판정

기관명이 등장하는 것과 기관을 사칭하는 것을 구분한다.

```text
현재 발화
+ 이전 2개 발화
+ 다음 1개 발화
```

문맥에서 자기소개, 소속 주장, 담당자 연결, 피해자 가족 주장 등이 확인될 때 사칭 라벨을 부여한다.

### 10.4 근거 보존

모든 자동 라벨에는 다음을 저장한다.

```text
evidence_turn_id
evidence_text
extraction_method
extraction_confidence
extraction_version
```

그래야 대시보드에서 해당 판정의 근거 문장을 확인할 수 있다.

## 16. 반드시 지킬 기준

- 기관이 언급되었다고 무조건 사칭으로 분류하지 않는다.
- 검찰과 경찰은 같은 공공기관 대분류 안에서 세부 유형으로 구분한다.
- 은행 이름·부서·직책·사람 이름을 하나의 컬럼에 합치지 않는다.
- 가족·지인은 관계가 명확히 언급된 경우에만 세부 관계를 부여한다.
- 한 사건의 복수 사칭과 복수 요구 행동을 여러 행으로 보존한다.
- 이름과 계좌 등 개인정보는 비식별화한다.
- 정확한 이름이나 직책이 나오지 않으면 추정하지 않는다.
- 자동 라벨에는 근거 발화와 추출 방법을 함께 기록한다.
- 자동 라벨을 사람 정답처럼 표현하지 않는다.
- 대시보드용 Boolean 컬럼은 상세 테이블에서 파생한다.
- 같은 파일 또는 통화가 학습·시험 양쪽에 들어가지 않게 한다.

## 결론

경찰·검찰·은행·가족·지인 사칭을 세밀하게 구분하는 것은 가능하다. 다만 이를 사건 테이블의 수많은 개별 컬럼으로 직접 관리하기보다 `vp_impersonations.csv`에서 **대분류, 세부 유형, 기관명, 부서명, 직책, 사람 이름, 피해자와의 관계, 사칭 방식, 근거 발화**를 각각 저장하는 것이 적절하다.

사건 테이블에는 대표 사칭 대상과 개수만 요약하고, 머신러닝 및 대시보드 단계에서 `has_prosecution_impersonation`, `has_bank_impersonation` 등의 변수를 자동 생성한다. 이 방식은 새로운 사칭 유형이 발견되어도 기존 데이터 구조를 크게 바꾸지 않고 확장할 수 있다.
